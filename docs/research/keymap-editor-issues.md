### Bugs and pain points

**Parser and round-trip failures.** This is the highest-risk lesson for our architecture. The old editor applied formatting to the whole document; its own formatting wiki says it runs a formatting pass over the entire DTS file. Reported consequences include lost inline-comment spacing ([#37](https://github.com/nickcoutsos/keymap-editor/issues/37)), address nodes becoming invalid syntax ([#39](https://github.com/nickcoutsos/keymap-editor/issues/39)), nested modifier functions with spaces being tokenized incorrectly ([#41](https://github.com/nickcoutsos/keymap-editor/issues/41)), custom `#define` bindings failing parse ([#103](https://github.com/nickcoutsos/keymap-editor/issues/103)), repeated macro parameters losing placeholders ([#158](https://github.com/nickcoutsos/keymap-editor/issues/158)), includes being rearranged or dropped ([#205](https://github.com/nickcoutsos/keymap-editor/issues/205), [#245](https://github.com/nickcoutsos/keymap-editor/issues/245)), and generated files failing to parse ([#210](https://github.com/nickcoutsos/keymap-editor/issues/210)). Local includes and preprocessor conditionals also make behavior definitions disappear or confuse layer detection ([#147](https://github.com/nickcoutsos/keymap-editor/issues/147), [#198](https://github.com/nickcoutsos/keymap-editor/issues/198), [#238](https://github.com/nickcoutsos/keymap-editor/issues/238)).

**Unsupported ZMK behaviors and parameter edge cases.** Users hit missing behavior choices and unsupported custom forms: mod-morph ([#38](https://github.com/nickcoutsos/keymap-editor/issues/38)), tap dance ([#73](https://github.com/nickcoutsos/keymap-editor/issues/73)), `&kt` ([#60](https://github.com/nickcoutsos/keymap-editor/issues/60)), arbitrary hold/tap keycodes ([#77](https://github.com/nickcoutsos/keymap-editor/issues/77)), argless hold-tap bindings ([#119](https://github.com/nickcoutsos/keymap-editor/issues/119)), nested behaviors ([#232](https://github.com/nickcoutsos/keymap-editor/issues/232)), and two-parameter Bluetooth behaviors in hold-tap ([#316](https://github.com/nickcoutsos/keymap-editor/issues/316)). Macros expose long strings and control semantics ([#89](https://github.com/nickcoutsos/keymap-editor/issues/89), [#127](https://github.com/nickcoutsos/keymap-editor/issues/127), [#227](https://github.com/nickcoutsos/keymap-editor/issues/227), [#254](https://github.com/nickcoutsos/keymap-editor/issues/254), [#344](https://github.com/nickcoutsos/keymap-editor/issues/344)).

**Combos and conditional layers.** Combo bugs included invisible combos ([#284](https://github.com/nickcoutsos/keymap-editor/issues/284)), a UI update that emitted `layers = <>` and disabled the combo ([#83](https://github.com/nickcoutsos/keymap-editor/issues/83)), and missing warnings for combo variables ([#197](https://github.com/nickcoutsos/keymap-editor/issues/197)). Conditional layers were repeatedly requested ([#64](https://github.com/nickcoutsos/keymap-editor/issues/64)); the maintainer later implemented them, but noted deletion of a referenced layer can leave invalid state. Our validator should check those references and reachability.

**Sensors, encoders, and mouse.** Encoder visibility/mapping issues: [#12](https://github.com/nickcoutsos/keymap-editor/issues/12), [#61](https://github.com/nickcoutsos/keymap-editor/issues/61), [#70](https://github.com/nickcoutsos/keymap-editor/issues/70), [#190](https://github.com/nickcoutsos/keymap-editor/issues/190), [#240](https://github.com/nickcoutsos/keymap-editor/issues/240). Mouse and pointing support is version-sensitive; an automatically inserted `<dt-bindings/zmk/pointing.h>` broke builds when users targeted older ZMK ([#292](https://github.com/nickcoutsos/keymap-editor/issues/292), [#340](https://github.com/nickcoutsos/keymap-editor/issues/340)); incorrect mouse move syntax also surfaced in [#283](https://github.com/nickcoutsos/keymap-editor/issues/283).

**Unicode, locale, and custom keycodes.** Glyph availability varied by OS/font ([#43](https://github.com/nickcoutsos/keymap-editor/issues/43)); international symbols and aliases required custom headers or hand edits ([#154](https://github.com/nickcoutsos/keymap-editor/issues/154), [#222](https://github.com/nickcoutsos/keymap-editor/issues/222), [#230](https://github.com/nickcoutsos/keymap-editor/issues/230), [#296](https://github.com/nickcoutsos/keymap-editor/issues/296), [#357](https://github.com/nickcoutsos/keymap-editor/discussions/357)). Keep the binding text even if no glyph is available and make labels platform-independent.

**Layout and info.json problems.** The layout metadata is separate from firmware bindings and must match binding order, matrix-transform selection, and key count. Issues include failed layout autogeneration ([#70](https://github.com/nickcoutsos/keymap-editor/issues/70), [#75](https://github.com/nickcoutsos/keymap-editor/issues/75), [#293](https://github.com/nickcoutsos/keymap-editor/issues/293), [#348](https://github.com/nickcoutsos/keymap-editor/issues/348)), malformed/misnamed info files ([#14](https://github.com/nickcoutsos/keymap-editor/issues/14), [#358](https://github.com/nickcoutsos/keymap-editor/issues/358)), key count/position mismatch ([#142](https://github.com/nickcoutsos/keymap-editor/issues/142), [#295](https://github.com/nickcoutsos/keymap-editor/issues/295), [#372](https://github.com/nickcoutsos/keymap-editor/issues/372)), and split/encoder layout gaps ([#104](https://github.com/nickcoutsos/keymap-editor/issues/104), [#190](https://github.com/nickcoutsos/keymap-editor/issues/190), [#240](https://github.com/nickcoutsos/keymap-editor/issues/240)). [#104](https://github.com/nickcoutsos/keymap-editor/issues/104) directly reports Advantage360 combo positions selecting keys on opposite sides of the board. Our board fixture must validate physical key-to-matrix indices independently of how the layout looks.

**GitHub auth, integration, and build status.** Users got stuck in app-installation setup or repo selection ([#49](https://github.com/nickcoutsos/keymap-editor/issues/49), [#65](https://github.com/nickcoutsos/keymap-editor/issues/65), [#192](https://github.com/nickcoutsos/keymap-editor/issues/192)); GitHub/API/host downtime broke login or commits ([#74](https://github.com/nickcoutsos/keymap-editor/issues/74), [#191](https://github.com/nickcoutsos/keymap-editor/issues/191), [#255](https://github.com/nickcoutsos/keymap-editor/issues/255)); incorrect branch/keymap selection was hard to diagnose ([#10](https://github.com/nickcoutsos/keymap-editor/issues/10), [#247](https://github.com/nickcoutsos/keymap-editor/issues/247)); build links could point to the wrong workflow ([#256](https://github.com/nickcoutsos/keymap-editor/issues/256)); and protected repo rulesets could be reported as read-only ([#370](https://github.com/nickcoutsos/keymap-editor/issues/370)). A “latest run” lookup is ambiguous when a repo has multiple workflows. Resolve a known workflow by ID/path and correlate it to the exact commit.

**UX complaints and multi-keyboard/split usage.** Beginners needed clearer build, save, and board setup guidance ([#122](https://github.com/nickcoutsos/keymap-editor/issues/122), [#176](https://github.com/nickcoutsos/keymap-editor/issues/176), [#314](https://github.com/nickcoutsos/keymap-editor/issues/314)); key selection was slow or awkward ([#90](https://github.com/nickcoutsos/keymap-editor/issues/90), [#111](https://github.com/nickcoutsos/keymap-editor/issues/111), [#113](https://github.com/nickcoutsos/keymap-editor/issues/113), [#226](https://github.com/nickcoutsos/keymap-editor/issues/226)); small text/low contrast and accessibility were raised ([#235](https://github.com/nickcoutsos/keymap-editor/issues/235), [#332](https://github.com/nickcoutsos/keymap-editor/issues/332), [#371](https://github.com/nickcoutsos/keymap-editor/issues/371)); accidental modal/tab dismissal lost work ([#374](https://github.com/nickcoutsos/keymap-editor/issues/374), [Discussion #338](https://github.com/nickcoutsos/keymap-editor/discussions/338)). Multiple keyboards/layouts in one repo and split positions increased selection complexity ([#26](https://github.com/nickcoutsos/keymap-editor/issues/26), [#80](https://github.com/nickcoutsos/keymap-editor/issues/80), [#242](https://github.com/nickcoutsos/keymap-editor/issues/242), [#312](https://github.com/nickcoutsos/keymap-editor/issues/312), [#367](https://github.com/nickcoutsos/keymap-editor/issues/367)).

### Why the GitHub integration is being discontinued

The maintainer’s wiki notice says they no longer want to maintain the project, that security work for managing the GitHub integration and the overhead of hosting the API server are the main operational burden, and that they want to wind those down while leaving the static app available. The notice does **not** give a dollar figure or say hosting cost alone was the reason. It also points users to Clipboard mode and Chromium File System access as continued alternatives. Source: [Discontinuing GitHub Integration](https://github.com/nickcoutsos/keymap-editor/wiki/Discontinuing-GitHub-Integration). The [limitations page](https://github.com/nickcoutsos/keymap-editor/wiki/Limitations-of-the-Keymap-Editor) says GitHub integration was the easiest route for general users to get firmware built. Discussion [#381](https://github.com/nickcoutsos/keymap-editor/discussions/381) confirms the discontinuation notice concerns the API/GitHub source, while the static editor can continue.

For our app, the single-user private GitHub App and server-only GitHub calls reduce the breadth of the security problem, but still leave a credential boundary and service availability to own. Keep permissions minimal, keep credentials server-side, state why an operation failed, and make exporting/recovering edited text possible when GitHub is unavailable.

## Prioritized recommendations

### Must for MVP

1. **Prove exact no-op round trips and patch only edited spans.** Preserve comments, whitespace, directives, includes, unknown nodes, and line endings; validate the exact bytes before/after. This is our Gate 1 and directly addresses [#37](https://github.com/nickcoutsos/keymap-editor/issues/37), [#39](https://github.com/nickcoutsos/keymap-editor/issues/39), [#205](https://github.com/nickcoutsos/keymap-editor/issues/205), and [#245](https://github.com/nickcoutsos/keymap-editor/issues/245). **Architecture:** already the CST + surgical patch design; make this a release gate.
2. **Keep unsupported syntax intact and visibly read-only.** Detect common preprocessor/include constructs enough to show a warning and avoid editing an affected range; do not expand arbitrary C macros. Evidence: [#103](https://github.com/nickcoutsos/keymap-editor/issues/103), [#147](https://github.com/nickcoutsos/keymap-editor/issues/147), [#198](https://github.com/nickcoutsos/keymap-editor/issues/198), [#238](https://github.com/nickcoutsos/keymap-editor/issues/238). **Architecture:** directly supported by the raw-node fallback.
3. **Validate the Advantage360’s physical positions against its actual matrix mapping.** Check both split halves, 76 rendered keys, skipped/non-key matrix indices, and combo key positions; use [#104](https://github.com/nickcoutsos/keymap-editor/issues/104) as the regression case. **Who:** Adv360 owner. **Architecture:** board-specific metadata plus mapping tests; layout coordinates alone are not sufficient.
4. **Make core binding editing tolerant of real ZMK parameters.** Cover nested modifiers, custom behavior parameters, hold-tap variants, argless bindings/placeholders, Bluetooth’s multi-parameter actions, and zero-valued timing fields. ## Parser fixtures to add

Use the source issue as provenance. These cases should be parsed, displayed, and round-tripped with no edits byte-for-byte; when a structured binding is changed, all unrelated bytes—including comments and directives—must remain unchanged.

1. **Inline comment spacing** — [#37](https://github.com/nickcoutsos/keymap-editor/issues/37) gives the minimal failing text:
   ```dts
   foo;         // bar
   ```
   The earlier formatter produced `foo;// bar`. Keep the exact gap on no-op and when patching another property.
2. **Preprocessor macro used as a binding** — [#103](https://github.com/nickcoutsos/keymap-editor/issues/103):
   ```c
   #define AS(keycode) &as LS(keycode) keycode
   / {
     keymap { default_layer { bindings = < AS(Q) >; }; };
   };
   ```
   This is a valid build input. Preserve the macro invocation as raw/unsupported rather than rejecting or expanding it.
3. **Local include at top level and inside `behaviors`** — [#198](https://github.com/nickcoutsos/keymap-editor/issues/198):
   ```dts
   #include "keymap_swiss_de.h"
   / { behaviors {
     #include "macros.dtsi"
   }; };
   ```
   The editor must not require fetching those files to preserve them. **Also verify include ordering and non-managed header retention** from [#205](https://github.com/nickcoutsos/keymap-editor/issues/205) and [#245](https://github.com/nickcoutsos/keymap-editor/issues/245). #245’s input includes `<dt-bindings/zmk/ext_power.h>`; the old save dropped it.
4. **Conditional compilation with duplicate layer names** — [#147](https://github.com/nickcoutsos/keymap-editor/issues/147) describes `#ifdef` branches that define alternative layouts and repeated layer identifiers. The issue links a real BT75 keymap but does not quote a minimal snippet. Use its linked source as the fixture; keep both branches and do not merge duplicate names into a fabricated layer.
5. **Addressed node syntax** — [#39](https://github.com/nickcoutsos/keymap-editor/issues/39):
   ```dts
   foo@123 {
     bar;
   };
   ```
   The old formatter rewrote this to invalid `foo { 123 ... }` syntax.
6. **Whitespace inside nested binding functions** — [#41](https://github.com/nickcoutsos/keymap-editor/issues/41):
   ```dts
   bindings = <&kp LS( LA(F))>;
   ```
   Parse nesting without treating spaces as argument boundaries.
7. **Repeated parameter placeholder in a macro** — [#158](https://github.com/nickcoutsos/keymap-editor/issues/158):
   ```dts
   bindings = <&macro_param_1to1 &kp MACRO_PLACEHOLDER
               &macro_param_1to1 &kp MACRO_PLACEHOLDER>;
   ```
   The issue’s generated output omitted the second `MACRO_PLACEHOLDER`; assert both occurrences survive.
8. **Combo all-layer default versus empty list** — [#83](https://github.com/nickcoutsos/keymap-editor/issues/83):
   ```dts
   combo_x { bindings = <&kp ESC>; key-positions = <1 2>; };
   ```
   Clearing a selected layer restriction should remove `layers`, not emit `layers = <>` (which disabled the combo).
9. **Managed versus user-owned headers** — [#292](https://github.com/nickcoutsos/keymap-editor/issues/292), [#340](https://github.com/nickcoutsos/keymap-editor/issues/340):
   ```c
   #include <dt-bindings/zmk/pointing.h>
   ```
   Never duplicate it or re-inject it solely because a parser recognizes a mouse behavior; a keymap built against an older ZMK must keep its own compatible include set.
10. **Macro-generated behaviors / missing root node** — [#238](https://github.com/nickcoutsos/keymap-editor/issues/238) supplies a real `zmk-helpers` example with `#define MAKE_HRM(...)` and `MAKE_HRM(...)` calls. It has no standalone minimal reproducer; keep the linked complete example as a raw-preservation fixture and verify the parser does not lose the root document when macro-generated nodes are present.
11. **Advantage360 matrix positions and combo indexes** — [#104](https://github.com/nickcoutsos/keymap-editor/issues/104) includes a 76-position matrix map and reports a rendered backslash combo as positions `<31 51>` on opposite sides. Add the exact reported map and assert matrix index ↔ displayed key mapping on both halves, with omitted pedal positions handled intentionally.
12. **Long macro and large patch payload** — [#344](https://github.com/nickcoutsos/keymap-editor/issues/344) reports a ~400-symbol macro failing to commit, and [#140](https://github.com/nickcoutsos/keymap-editor/issues/140) reports a large keymap hitting `PayloadTooLargeError`. Round-trip a large macro and ensure the server patch path has no silent truncation/size failure.

## Lessons for our design

- Treat original source text as the authority. The old project’s formatting pass was a recurring source of include, comment, and node corruption. The lossless CST and bounded patch model is a direct answer to that evidence.
- Unknown syntax must remain useful: show it in context, preserve it, and explain which editor features cannot reason about it. Do not pretend a successful parse means semantic support.
- Do not execute user preprocessor code to make the UI work. The wiki notes arbitrary macro/include graphs, custom ZMK forks, server compute, and the difficulty of recreating the author’s original abstractions on save. Support a narrow syntax surface with raw preservation.
- A keyboard drawing is not enough to establish key identity. Verify ordered binding slots against the board matrix transform, including split sides, skipped positions, encoders and combos. The Advantage360 report makes this especially important for our own board.
- Schema types need semantic overlays. A YAML `int` does not explain a layer enum, modifier bitset, or a behavior-specific parameter contract. Keep behavior metadata versioned and provide raw-value escape hatches.
- Keep GitHub operations explicit and deterministic. Auth/install/repo/branch errors, server outages, ambiguous build runs, and protected branches all surfaced in real use. Resolve builds against our configured workflow and the exact commit; never infer the desired artifact from “most recent run.”
- Put novice context at the point of action. Several users could not tell whether Save wrote source, started a build, changed the keyboard, or flashed firmware. Our status copy should name those steps and keep flashing out of the app.
- Reversible editing and visible diffs are core trust features, not polish. A user lost over an hour after a key assignment closed a browser tab ([#374](https://github.com/nickcoutsos/keymap-editor/issues/374)). Protect in-progress modal state and make each remote write inspectable.
